## Findings

### High: merged RMP isolation is not deployed

Read-only inspection of the connected `bye-dev` project found `bye-api` v26 and `bye-sync` v4, with no `bye-rmp` function. The background scheduling table and active `bye-rmp-background` cron job are absent. The deployed v26 source inspected earlier still enables source retrieval on ordinary authenticated RMP requests. Consequently the new cache-only guarantee does not yet describe the live backend. GitHub `main` is merge commit `97a2df80eb381c52284cfb5f55d11fcfc80050b0`.

**Action:** reconcile the documented deployed source differences before deployment. Test the migration and scheduled worker in isolation, and only then plan a coordinated rollout. Avoid triggering RMP during this audit.

### Accepted tradeoff: search history persists across device lock

In `frontEnd/bye-web/src/main.tsx`, `search()` saves the most recent five course, school, semester and route entries under `bye-web:recent` in persistent browser storage. `lockDevice()` and the access-lost handler clear session views and sign out but do not clear that stored history. The next person using the same browser profile can see recent searches. This reveals interest in courses, not proof of enrollment. `courseSearch.ts` also caches search queries and results in local storage; its retention and cleanup deserve review.

**Owner decision:** Accept this behavior. BYE is expected to be used mostly on personal devices during a short registration period, and retaining recent searches is useful for returning visits. No fix is requested. On a shared browser profile, a later user may see those searches; the Recent section provides a Clear control. This observation follows from code inspection; a physical shared-device test was not performed.

### Deployment risk: frontend/backend versions must move together

The merged frontend sends POST requests for RMP candidate, profile and review reads. Deployed `bye-api` v26 accepts GET for those routes and POST only for refresh. If the new frontend is deployed while v26 remains active, those requests can fail. The deployed frontend version was not inspected, so this is a compatibility risk, not a confirmed current outage.

### Platform advisories to investigate

Supabase security advisors flag [pg_net in the public schema](https://supabase.com/docs/guides/database/database-linter?lint=0014_extension_in_public), [policies applying to anonymous sign-ins on cron tables](https://supabase.com/docs/guides/database/database-advisors?queryGroups=lint&lint=0012_auth_allow_anonymous_sign_ins), and [disabled leaked-password protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection). These are configuration warnings, not proof of exploitation. Assess actual grants, exposed schemas and whether password authentication is used before changing anything.

Thirty backend tables have RLS enabled with no policies. In this architecture that can intentionally deny browser access; it is not itself a vulnerability. A read-only privilege query found no direct SELECT grants to `anon` or `authenticated` on BYE tables and views. Among `public.bye_*` functions, only the invoker `bye_code_alias` had execute privileges for those roles. These are catalog checks, not a substitute for authenticated end-to-end access testing.

Performance advisors flagged [two foreign keys without covering indexes](https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys), on `bye_course_reference` and `bye_saved_professors`. Measure real query plans and write overhead before adding indexes. One reportedly unused index is not sufficient evidence to remove it.

- Local backend suite: **73 passed**. Local frontend suite: **89 passed**, using dummy Supabase configuration.
- Existing tests cover membership checks, access isolation, cache behavior, rate gates, RMP payload isolation, and scheduler claims. They do not prove absence of all leaks or vulnerabilities.
- No separate staging project was found in the connected project list. No live accounts, production settings, scheduled jobs or secrets were modified. No requests were sent to RMP.

Tests exercised those local files, not a fresh checkout of the merged commit. Live watches and education helper modules are absent locally, so they were not fully audited.
